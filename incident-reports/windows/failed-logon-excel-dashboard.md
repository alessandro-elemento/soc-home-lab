## Report: Failed Logon Analysis in Excel (Dashboard from CloudWatch Data)

**Environment:** Windows 11 Home (ARM64, build 10.0.26200), isolated VirtualBox lab VM
(Windows11-Victim); analysis done in Microsoft Excel on the host Mac
**Date:** 10 November 2026
**Technique:** T1110.001: Brute Force - Password Guessing (Credential Access)
**Tools:** CloudWatch Logs Insights (CSV export), Microsoft Excel (formulas, `XLOOKUP`,
pivot tables, charts)
**Workbook:** [`dashboards/failed-logon-dashboard.xlsx`](../../dashboards/failed-logon-dashboard.xlsx)
**Methodology:** [`dashboards/README.md`](../../dashboards/README.md), covering every sheet,
formula and design choice

### Summary

The earlier failed-logon reports reproduced the same detection in Splunk, AWS CloudWatch and
Python. This exercise reproduces it in Excel and presents the result as a one-page summary
for a non-technical reader, with the working data and pivot tables behind it. The point was
to practise turning raw security events into something a manager or risk committee could
read, not to find an attack: every event came from my own deliberate tests.

### Data

The 18 failed-logon events (Windows Security Event ID 4625) were exported from CloudWatch
Logs Insights as CSV. They were shipped to CloudWatch by the PowerShell script from the
[CloudWatch report](failed-logon-detection-cloudwatch.md), which I ran by hand for this
exercise because the scheduled task had already been removed. They come from three rounds of
testing:

- 5 October 2026 (Sydney 6 October): six wrong-password attempts at the lock screen.
- 6 October 2026: three more.
- 9 to 10 November 2026: a further round that included four attempts using usernames that do
  not exist (`runas /user:<name> cmd` with a wrong password), plus one failure caused by
  Windows forcing a password change.

### How the workbook is built

- **Time columns.** The export is in UTC, so a Sydney-time column adds 11 hours
  (`=H3+11/24`). That figure is hard-coded for daylight saving and would be 10 hours in winter.
- **Alert rule.** To mirror the CloudWatch alarm, each event is put into a 5-minute bucket
  (`=FLOOR(H3, "0:05")`), the events in each bucket are counted (`COUNTIF`), and a bucket
  with 3 or more is flagged `ALERT`.
- **Counting windows, not rows.** Counting alert rows would give 17, because every row in a
  flagged bucket is flagged. A weight column gives each alert row 1 divided by the size of
  its bucket, so each alert window adds up to exactly 1 and the total is 3.
- **Reason lookup.** A small `Meaning` sheet maps each `SubStatus` code to plain English,
  and an `XLOOKUP` column applies it to each row.
- **Pivot tables and charts.** Three pivots (by username, by hour, by reason) feed the charts
  on the Summary sheet.

### Results

| Figure | Value |
|---|---|
| Total failed logons | 18 |
| Alert windows (5-minute periods with 3 or more failures) | 3 |
| Distinct usernames | 5 |
| Attempts against non-existent usernames | 4 |

By reason: 13 wrong password for an existing account (`0xc000006a`), 4 username does not
exist (`0xc0000064`), 1 password expired (`0xc0000071`).

By Sydney hour: 9 in hour 5, 6 in hour 6 and 3 in hour 22.

### Analysis

- The two main failure types look different in the data. Wrong-password failures are all for
  `kal` from `127.0.0.1`, while the non-existent usernames come from `::1`. In a real
  environment, many different usernames that do not exist would suggest username guessing,
  while repeated failures against one valid account suggest password guessing.
- The one `0xc0000071` row was not an attack. Windows prompted me to change my password at
  that time. I labelled it "password expired (forced password change)" from that prompt and
  from my understanding of the code, and I did not check the event's failure reason text in
  Event Viewer.
- All activity was my own deliberate testing, so the correct classification is benign. This
  validates the analysis method, not a real detection.

### Limitations

- Only 18 events from one VM, all generated by me. The charts demonstrate the method and say
  nothing about real attack patterns.
- Fixed 5-minute buckets can split a burst, so three failures straddling a bucket boundary
  would be counted as two and one and would not flag. The CloudWatch alarm's fixed period has
  the same weakness.
- The Sydney-time offset is hard-coded and would need changing outside daylight saving.
- The pivot tables do not refresh by themselves; they need refreshing after the data changes.
- The summary figures are formulas over fixed cell ranges (`B3:B20` and so on), so they would
  need extending if rows were added.
- Personal metadata (last-modified-by name and local folder path) was removed from the
  uploaded file.

### Conclusion

This exercise recreated a threshold detection in Excel with formulas, built a lookup to turn
status codes into plain English, summarised the data with pivot tables and charts, and
packaged it as a one-page view with its limitations stated.
